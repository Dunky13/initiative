Decisions and compatibility

  • Frontend code continues using JavaScript Date/date-fns. The fix distinguishes calendar dates, local wall time, absolute instants and elapsed durations; it is not a blanket Temporal migration. No new runtime dependency was added.
  • A new or changed ambiguous/nonexistent local time is explicitly rejected with a localized error. An unchanged imported timestamp retains its original instant, including which side of a repeated hour it names. The UI does not add a new timezone or fold-selection control.
  • Existing fixed-instant recurrence and rolling tasks' completer-local-day semantics remain intentional. Month-end skip semantics for custom RRULEs are not silently rewritten. Calendar-window parameters that explicitly document naive input as UTC retain that policy.
  • Instant-valued calendar and notice write inputs now require Z or an explicit UTC offset. Date-only values and iCal floating values have separate existing resolution paths. Older clients sending timezone-less instant strings receive validation errors and must include the offset.
  • QueryColumnDescription.date_only is additive; numeric epoch values on the wire are unchanged. SQL DATE is formatted as a calendar date, while timestamptz and other instant-valued fields retain viewer-local formatting.
  • The generated API client is regenerated from the backend OpenAPI definition. Task reads expose the anchor metadata; project export/import also carries it, while older envelopes remain accepted.

Migration and rollback

backend/alembic/versions/20261020_0528_fixed_task_recurrence_anchor.py follows 20261019_0526, adding tasks.recurrence_anchor (nullable timestamptz) and tasks.recurrence_anchor_count (non-null integer, default 0) to each guild schema. New guild schemas derive their columns from current model metadata. At implementation time, open PR #2912 independently adds migration 0527. Both PRs currently follow 0526; whichever lands second must rebase and chain its migration to the new head before merging. This PR does not edit #2912's migration.

Backfill uses the current effective carried due/start and the existing consumed count. A surviving original task cannot prove whether a later intentional following-series edit changed phase, so the migration preserves the current continuation rather than guessing historical intent. Already-lost historical phase cannot be reconstructed. Legacy counts may have included extra dates; the migration conservatively retains that consumption rather than restarting COUNT.

The downgrade drops the two added columns. Code can be rolled back, but dropping anchor state and later re-upgrading cannot recover intervening phase history. Back up the database before an operational downgrade. No production migration or deployment was performed as part of this task.

Validation

The initial combined frontend run passed 146 tests in 15 files. The shared calendar/locale follow-up passed 441 tests in 3 files (overlapping calendar coverage; these counts are not additive). The production Vite bundle built. Backend query/calendar endpoint validation passed 104 tests; the final recurrence/statistics/query batch passed 322 tests. The branch was then rebased onto efbef4e7a (the shared recurrence owner from PR #2914), preserving that refactor. The post-integration batch passed 288 tests, including the added fixed-to-rolling COUNT lifecycle regression and all shared completion/skip callers.

A real browser loaded the actual CalendarView and DateTimePicker components with fixture data, in Europe/Amsterdam, at 1280px and 390px widths. It confirmed 09:00 at the 09:00 row, separate lanes for overlapping backwards-clock markers, a 15:00 slot callback, and no horizontal overflow at 390px. Typing February 30, a spring gap time and an autumn fold time produced an error without changing the saved value. This is component/browser evidence, not a signed-in application journey or external calendar-provider compatibility proof.

Independent source review found additional edit/carry, fold-default, lane and midnight-gap cases; regression tests reproduced them and the fixes passed. Cross-provider review was skipped because that reviewer subscription is unavailable. No skipped review is represented as approval.

No production migration, release or deployment was attempted. External calendar clients and device WebViews were not exercised.
